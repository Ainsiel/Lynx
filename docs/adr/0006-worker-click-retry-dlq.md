# Worker agregador: dedup, retry con backoff y DLQ

El worker consume `clicks.ingest` con `amqplib` puro, prefetch 1 y acks manuales. La deduplicación la garantiza la BD: `clicks.event_id` es UNIQUE y el `INSERT ... ON CONFLICT DO NOTHING` devuelve 0 filas si el evento ya se procesó, omitiendo entonces la agregación — un mismo eventId redeliverado (retry o reinicio) cuenta una sola vez. La persistencia (click + `daily_stats`/`stats_country`/`stats_device`) ocurre en una única transacción, con upserts atómicos `ON CONFLICT ... DO UPDATE SET clicks = clicks + 1` (nunca SELECT + UPDATE). El día se agrupa en UTC.

Los fallos transitorios se reintentan con backoff exponencial (base 1s, ×2, máx 3 entregas) y requeue por **republish**: el worker ackea el original y publica una copia a `clicks.ingest` estampando el header `x-lynx-retries`, tras esperar el backoff. Al vivir el contador en el mensaje (no en el consumidor), el límite "máx N" se mantiene aunque la cola la atiendan varias instancias del worker. Los fallos persistentes (payload inválido, slug inexistente, fecha inválida) — y los transitorios que agotan entregas — se enrutan a la DLQ: la cola `clicks.ingest` declara `x-dead-letter-exchange: clicks.dlx` y `x-dead-letter-routing-key: clicks.dlq`, y el `nack(requeue=false)` entrega el mensaje a `clicks.dlq` para inspección/reproceso manual. La topología completa (exchange `clicks`, DLX, colas y bindings) la declara el worker; la API publica con `noAssert` para no competir por la declaración de la cola y dejar fijos los argumentos de dead-letter.
